# Инструкции для Codex

Transcribation — локальное Windows-приложение. Архитектура: модульный монолит,
src-layout, пакет `src/local_transcriber`, тесты в `tests/` в корне проекта.
Целевая среда: Windows 11 x64, RTX 4060 Ti 8 GB, русский язык, локальная обработка.
Python окончательно выбран: CPython 3.14 x64 с GIL, >=3.14,<3.15.
Не менять эту версию из-за рисков совместимости; фиксировать риск и план проверки.

- Перед задачей прочитай релевантные документы: `docs/ORIGINAL_TZ.md`,
  `docs/requirements.md`,
  `docs/architecture.md`, `docs/progress.md`, `docs/decisions.md`,
  `docs/CODEX_PROMPTS_V2.md` (и исходник по ссылке), `docs/implementation_plan.md`.
- Требования нормализуются только в `docs/requirements.md`, статусы и результаты
  проверок — только в `docs/progress.md`. Промпты не заменяют оригинальное ТЗ.
  При отсутствии оригинала для шага 00 используй BLOCKED FOR REQUIREMENTS.
  Оригинал сохраняй; при синхронизации не теряй FR/NFR и требования без ID.
- Выполняй только запрошенный этап. Не реализуй будущие этапы без необходимости
  для текущей задачи; не начинай следующий этап самостоятельно.
- Соблюдай границы модулей и разделение ответственности. Domain не зависит от
  GUI, SQLAlchemy, FFmpeg и движка распознавания. GUI и GPU worker — разные процессы.
- Используй type hints для публичных интерфейсов. Глобальное изменяемое состояние
  допускается только с явным обоснованием.
- Обрабатывай длинные медиафайлы потоково или ограниченными чанками, не загружай
  их целиком в RAM. Исходные медиафайлы храни вне PostgreSQL.
- Не отправляй аудио, видео и транскрипты во внешние сервисы. Не добавляй облачные
  AI API без явного согласования. Не храни секреты в исходном коде.
- RAW неизменяем; READABLE и MANUAL — отдельные версии. Время — integer
  milliseconds. Не используй `shell=True`; будущие интеграционные тесты БД
  должны работать с отдельной test DB, не с пользовательской базой.
- Не выдавай фиктивные реализации и заглушки за готовую функциональность.
  Документация должна различать реализованное и запланированное.
- Для новой бизнес-логики добавляй тесты. Перед завершением запускай доступные
  проверки, соответствующие изменениям. Сообщай команды и результаты; не утверждай,
  что тесты прошли, если они не выполнялись или не было собрано ни одного теста.
- Не меняй архитектурные решения молча. Значимые решения и изменения фиксируй
  в `docs/decisions.md`, после каждого этапа обновляй `docs/progress.md`.
- Не выполняй `git commit` или `git push` без явного разрешения пользователя.
- Не удаляй пользовательские файлы и не выполняй разрушительные операции без
  согласования. Сохраняй чужие незакоммиченные изменения.
