# Техническое задание
## Разработка локальной системы транскрибации длинных аудио- и видеозаписей

**Наименование проекта:** LocalTranscriber

**Версия ТЗ:** 1.0

**Тип приложения:** Desktop application

**Целевая ОС:** Windows 11 x64

**Оборудование:** NVIDIA GeForce RTX 4060 Ti, 8 GB VRAM

**Основной язык распознавания:** русский

**Основной стек:** Python, PostgreSQL, faster-whisper, PySide6

**Режим работы:** полностью локальный, без обязательного подключения к интернету после установки и загрузки моделей.

---

# 1. Назначение системы

Разработать локальное приложение, предназначенное для автоматического преобразования длинных аудио- и видеозаписей в структурированный текст.

Основной источник материалов — записи, полученные с помощью OBS Studio.

Программа должна позволять пользователю выбрать видеозапись, выполнить распознавание русской речи с использованием локальной AI-модели, обработать результат для улучшения читаемости, сохранить его в базе данных и экспортировать в удобный формат.

### 1.1. Основные цели

1. Исключить необходимость использования платных сервисов транскрибации.
2. Обеспечить обработку записей продолжительностью от нескольких минут до многих часов.
3. Поддерживать файлы большого размера без полной загрузки в оперативную память.
4. Использовать NVIDIA GPU для ускорения распознавания.
5. Получать читаемый текст с сохранением исходного смысла.
6. Сохранять результаты и историю обработки в PostgreSQL.
7. Обеспечить возможность восстановления незавершённой обработки после сбоя.
8. Предоставить удобный графический интерфейс на русском языке.

### 1.2. Ограничения первой версии

В первой версии не требуется:

- Транскрибация микрофона в реальном времени.
- Облачная синхронизация.
- Мобильное приложение.
- Регистрация пользователей и авторизация.
- Обучение собственной нейросети.
- Распределённая обработка на нескольких компьютерах.
- Автоматическое составление конспектов с помощью дополнительной LLM.

Архитектура должна допускать добавление перечисленных возможностей в будущем.

# 3. Функциональные требования

## FR-01. Импорт файлов

Пользователь должен иметь возможность выбирать файлы через графический интерфейс.

**Поддерживаемые форматы:**

- MKV
- MP4
- MOV
- MP3
- WAV
- M4A
- FLAC
- WEBM

### Требования

1. Выбор одного или нескольких файлов.
2. Поддержка drag-and-drop.
3. Проверка существования и доступности файла.
4. Анализ содержимого с помощью ffprobe.
5. Получение длительности, размера, контейнера, кодеков и числа аудиопотоков.
6. Определение файлов без аудиодорожек.
7. Проверка доступного места для временных данных.
8. Отображение ошибок для повреждённых или неподдерживаемых файлов.

Программа не должна отклонять файл исключительно из-за размера 1 ГБ, 5 ГБ или более.

Практические ограничения определяются свободным местом на диске, доступностью файла, кодеком и продолжительностью записи.

## FR-02. Выбор аудиодорожки

OBS может записывать несколько независимых аудиодорожек.

При импорте необходимо показывать список доступных аудиопотоков.

Для каждого потока отображать:

- Номер потока.
- Кодек.
- Число каналов.
- Частоту дискретизации.
- Языковую метку, если она присутствует.

**Режимы обработки:**

1. Одна выбранная дорожка.
2. Несколько выбранных дорожек по отдельности.
3. Смешивание нескольких дорожек по запросу пользователя.

Раздельная обработка предпочтительна при наличии независимых дорожек микрофона и системного звука.

Программа не должна автоматически предполагать, что конкретная дорожка принадлежит определённому человеку.

Назначение ролей «Я», «Собеседник» и «Неизвестный» должно настраиваться пользователем.

Для смешанных дорожек автоматическое разделение говорящих не требуется в MVP.

## FR-03. Подготовка аудио

После выбора дорожки приложение должно выполнять потоковое декодирование звука.

### Требования

- Использовать FFmpeg.
- Не декодировать весь видеофайл в RAM.
- Не выполнять перекодирование видеопотока.
- Подготавливать аудио в формате mono PCM, 16 kHz для модели распознавания.
- Сохранять информацию об исходных временных метках.
- Обрабатывать стерео и многоканальные записи.
- Обеспечить корректное завершение дочерних процессов FFmpeg при отмене задания.

Декодирование должно осуществляться небольшими ограниченными по памяти фрагментами.

Длина рабочего участка на первом этапе: **5 минут**, настраиваемый диапазон — 1–15 минут.

Фрагмент длительностью 5 минут не обязан целиком находиться в памяти, если используется последовательная обработка внутренних речевых сегментов.

## FR-04. Определение речевой активности

Для исключения тишины используется Silero VAD.

Функции:

1. Определять участки, содержащие речь.
2. Исключать длительные паузы из AI inference.
3. Сохранять таймкоды исходной записи.
4. Не обрезать начало и конец слов.
5. Поддерживать настройку чувствительности.

**Начальные параметры:**

- Sample rate: 16000 Hz.
- Speech threshold: 0.5.
- Минимальная пауза: 500 мс.
- Padding вокруг речи: 200 мс.
- Максимальная длина речевого фрагмента: ориентировочно 30 секунд, если это необходимо для выбранного алгоритма.

VAD не должен считаться безошибочным. Необходимо сохранять возможность повторной обработки участка с изменёнными параметрами.

## FR-05. Распознавание речи

Основной движок — faster-whisper.

**Базовая модель:** large-v3-turbo.

**Дополнительные модели:** medium, large-v3.

**Начальная конфигурация:**

- Device: CUDA.
- Compute type: float16.
- Fallback compute type: int8_float16.
- Language: ru.
- Task: transcribe.
- Начальный beam size: 5.
- Температура декодирования: 0 с настраиваемой стратегией повторной попытки.

### Обязательные возможности

1. Загрузка модели при запуске worker-процесса.
2. Повторное использование загруженной модели.
3. Распознавание фрагментов аудио.
4. Получение текста и таймкодов.
5. Сохранение информации о модели и параметрах.
6. Корректная обработка недостатка VRAM.
7. Возможность изменения модели в настройках.
8. Повторная обработка отдельного участка.

Параметры должны подбираться по результатам тестирования, а не считаться универсально оптимальными.

Дополнительный режим получения таймкодов отдельных слов должен быть реализован как опциональный, поскольку может повышать вычислительные затраты.

## FR-06. Обработка длинных записей

Длительность записи не должна ограничиваться продолжительностью аудио, которую модель может обработать за один вызов.

### Алгоритм

1. Определить параметры исходной записи.
2. Создать задание в PostgreSQL.
3. Разделить запись на логические рабочие участки.
4. Последовательно извлекать аудио выбранной дорожки.
5. Выполнить VAD и распознавание.
6. Сохранить полученные сегменты.
7. Зафиксировать успешное завершение участка.
8. Перейти к следующему участку.
9. Собрать полный транскрипт.

### Границы участков

Необходимо учитывать, что слова и предложения могут пересекать границы рабочих участков.

Реализовать:

- Небольшое перекрытие на границах.
- Пересчёт локальных временных меток в абсолютные.
- Сопоставление соседних результатов.
- Удаление дублирующихся фрагментов.
- Защиту от потери слов на границах.

Дедупликация не должна удалять реальные повторения речи без достаточных оснований.

### Работа с памятью

Необходимо гарантировать ограниченное потребление RAM, не зависящее линейно от общей продолжительности файла.

Большие PCM-массивы не должны храниться в PostgreSQL или передаваться через БД.

## FR-07. Восстановление после прерывания

Система должна сохранять прогресс обработки.

Поддерживаемые состояния задания:

- PENDING — ожидает выполнения.
- ANALYZING — анализ исходного файла.
- PROCESSING — идёт распознавание.
- PAUSED — приостановлено пользователем.
- INTERRUPTED — выполнение прервано.
- COMPLETED — успешно завершено.
- FAILED — завершено с ошибкой.
- CANCELLED — отменено пользователем.

### Требования

1. Сохранять прогресс после каждого успешно обработанного участка.
2. При закрытии приложения не терять подтверждённые результаты.
3. При запуске обнаруживать ранее прерванные задания.
4. Предлагать продолжить обработку.
5. Проверять доступность и неизменность исходного файла.
6. Не создавать дубли в базе при повторном запуске.
7. Не отмечать участок завершённым до сохранения его результата.

Для надёжности сохранение сегментов и изменение статуса участка должны происходить в одной транзакции PostgreSQL.

При восстановлении необходимо повторно обработать незавершённый участок.

## FR-08. Приведение текста к читаемому виду

Это одна из ключевых функций приложения.

Необходимо разделить **исходную транскрипцию** и **отредактированную версию текста**.

### Исходный текст

Хранит результат распознавания модели без смыслового переписывания.

### Читаемый текст

Создаётся на основе исходного транскрипта с целью улучшения восприятия.

Допустимые преобразования:

- Восстановление пунктуации.
- Разделение на предложения.
- Формирование абзацев.
- Исправление очевидных технических ошибок форматирования.
- Приведение пробелов и регистра к нормальному виду.
- Нормализация написания известных терминов.
- Опциональное удаление слов-паразитов и речевых повторов.

**Категорически запрещено в режиме точной транскрибации:**

- Придумывать отсутствующие фразы.
- Заменять смысл сказанного.
- Удалять существенную информацию.
- Подменять неизвестные слова догадками без обозначения неопределённости.
- Представлять пересказ как дословный транскрипт.

### Режимы текста

**Режим A — Дословный**

Максимально близкое воспроизведение произнесённой речи.

**Режим B — Читаемый**

Абзацы, пунктуация, нормализация оформления и осторожное устранение несущественных речевых дефектов.

**Режим C — Ручное редактирование**

Пользователь самостоятельно изменяет результат в интерфейсе.

Для MVP режим B должен использовать детерминированную обработку и безопасные правила редактирования. Подключение локальной LLM для более сложной редакторской обработки предусматривается отдельным этапом.

При редактировании всегда должна сохраняться исходная версия.

# 5. Архитектура программного обеспечения

Использовать модульный монолит.

Не создавать микросервисную архитектуру для первой версии.

## 5.1. Основные модули

**UI Layer**

Отвечает за взаимодействие с пользователем, отображение состояния заданий и редактирование транскриптов.

**Application Layer**

Управляет сценариями работы, очередью заданий, отменой и восстановлением.

**Media Layer**

Работает с FFmpeg, извлекает аудио, анализирует потоки и обрабатывает таймкоды.

**Transcription Layer**

Содержит адаптер faster-whisper, загрузчик моделей и логику распознавания.

**Text Processing Layer**

Формирует читаемый текст, обрабатывает терминологию и сохраняет версии.

**Persistence Layer**

Работает с PostgreSQL, транзакциями, миграциями и репозиториями.

**Export Layer**

Генерирует TXT, JSON, SRT и Markdown.

## 5.2. Фоновые процессы

Графический интерфейс и процесс AI inference должны быть изолированы.

Предлагаемая схема:

- Главный процесс: PySide6.
- Отдельный worker-процесс: декодирование и GPU inference.
- PostgreSQL: состояние заданий и результаты.
- Очереди межпроцессного взаимодействия: команды и уведомления.

В первой версии допускается один активный GPU-worker.

Одновременное распознавание нескольких больших файлов на 8 ГБ VRAM не требуется.

Несколько заданий должны выполняться последовательно через очередь.

## 5.3. Управление worker-процессом

Команды:

- START_JOB
- PAUSE_JOB
- RESUME_JOB
- CANCEL_JOB
- SHUTDOWN

События:

- JOB_STARTED
- PROGRESS_UPDATED
- CHUNK_COMPLETED
- JOB_PAUSED
- JOB_COMPLETED
- JOB_FAILED

Процесс должен корректно освобождать ресурсы после завершения задания.

При аварийном завершении worker главный процесс должен отобразить ошибку и обеспечить возможность повторного запуска.

# 7. Проектирование PostgreSQL

PostgreSQL должен хранить метаданные и структурированные результаты обработки.

**Исходные видеофайлы не должны сохраняться в PostgreSQL.**

Хранить путь к исходному файлу и его идентификаторы.

## 7.1. Таблица media_files

Назначение: хранение информации об исходных файлах.

Поля:

- id — UUID, первичный ключ.
- file_path — TEXT.
- filename — TEXT.
- file_size_bytes — BIGINT.
- duration_ms — BIGINT.
- container_format — VARCHAR.
- audio_streams_count — INTEGER.
- file_fingerprint — VARCHAR.
- created_at — TIMESTAMPTZ.

## 7.2. Таблица transcription_jobs

Назначение: хранение заданий.

Поля:

- id — UUID.
- media_file_id — UUID, внешний ключ.
- status — VARCHAR.
- model_name — VARCHAR.
- language — VARCHAR.
- parameters — JSONB.
- progress_percent — NUMERIC.
- total_chunks — INTEGER.
- completed_chunks — INTEGER.
- started_at — TIMESTAMPTZ.
- finished_at — TIMESTAMPTZ.
- error_message — TEXT.
- created_at — TIMESTAMPTZ.

## 7.3. Таблица audio_streams

Назначение: описание аудиодорожек.

Поля:

- id — UUID.
- media_file_id — UUID.
- stream_index — INTEGER.
- codec — VARCHAR.
- sample_rate — INTEGER.
- channels — INTEGER.
- role_label — VARCHAR, nullable.

## 7.4. Таблица processing_chunks

Назначение: контроль обработки длинных записей.

Поля:

- id — UUID.
- job_id — UUID.
- stream_id — UUID.
- chunk_index — INTEGER.
- start_ms — BIGINT.
- end_ms — BIGINT.
- status — VARCHAR.
- attempt_count — INTEGER.
- completed_at — TIMESTAMPTZ.
- error_message — TEXT.

Ограничение уникальности:

(job_id, stream_id, chunk_index)

Это позволяет безопасно повторять обработку после ошибок.

## 7.5. Таблица transcript_segments

Назначение: хранение реплик.

Поля:

- id — UUID.
- job_id — UUID.
- chunk_id — UUID.
- stream_id — UUID.
- start_ms — BIGINT.
- end_ms — BIGINT.
- raw_text — TEXT.
- speaker_label — VARCHAR.
- segment_index — INTEGER.
- metadata — JSONB.
- created_at — TIMESTAMPTZ.

Индексы:

- job_id.
- (job_id, start_ms).
- chunk_id.

Хранение таймкодов в целых миллисекундах предпочтительнее использования float в БД.

## 7.6. Таблица transcript_versions

Назначение: хранение версий текста.

Поля:

- id — UUID.
- job_id — UUID.
- version_number — INTEGER.
- version_type — VARCHAR.
- content — TEXT.
- processing_metadata — JSONB.
- created_at — TIMESTAMPTZ.

Типы версий:

- RAW
- READABLE
- MANUAL

Ручное редактирование не должно перезаписывать RAW-транскрипт.

## 7.7. Таблица custom_terms

Назначение: словарь терминов.

Поля:

- id — UUID.
- canonical_form — VARCHAR.
- variants — JSONB.
- enabled — BOOLEAN.
- created_at — TIMESTAMPTZ.

## 7.8. Общие правила хранения

- Использовать миграции Alembic.
- Применять внешние ключи.
- Обеспечить атомарное сохранение результатов участка.
- Использовать параметризованные запросы.
- Не сохранять секреты подключения в логах.
- Предусмотреть удаление задания вместе с его результатами.
- Не удалять исходный медиафайл при удалении задания без отдельного явного действия пользователя.

# 8. Алгоритм полного цикла обработки

**Этап 1. Импорт**

Пользователь выбирает OBS-запись.

Приложение проверяет файл, запускает ffprobe и получает метаданные.

**Этап 2. Создание задания**

В PostgreSQL создаются записи исходного файла и задания на транскрибацию.

**Этап 3. Подготовка**

Определяются выбранные дорожки, модель, язык и параметры.

**Этап 4. Инициализация AI**

Worker загружает модель в память GPU.

**Этап 5. Обработка**

Файл последовательно декодируется, выделяются речевые фрагменты, выполняется распознавание.

**Этап 6. Сохранение**

Сегменты записываются в PostgreSQL с абсолютными таймкодами.

**Этап 7. Объединение**

Результаты всех участков упорядочиваются по времени. Устраняются технические дубли на границах.

**Этап 8. Форматирование**

Создаётся читаемая версия транскрипта.

**Этап 9. Завершение**

Задание получает статус COMPLETED.

**Этап 10. Экспорт**

Пользователь получает итоговый файл в выбранном формате.

# 9. Нефункциональные требования

## NFR-01. Производительность

Целевое оборудование: RTX 4060 Ti 8 GB.

Требования:

1. GPU должен использоваться для поддерживаемых операций распознавания.
2. Интерфейс должен оставаться отзывчивым во время обработки.
3. Объём используемой RAM не должен возрастать пропорционально длине записи.
4. Одновременно должна работать не более одной задачи GPU inference.
5. Пользователь должен видеть текущий прогресс.
6. Должны измеряться скорость обработки и фактическая загрузка ресурсов.

**Предварительная целевая производительность:** обработка часовой записи за 15 минут или меньше на тестовом наборе при использовании рекомендованной модели и GPU.

Это инженерный целевой показатель, а не гарантированная скорость. Он должен быть проверен бенчмарком на реальном оборудовании. Если цель не достигнута, требуется профилирование и документирование причин.

## NFR-02. Потребление памяти

- Ограничить объём очередей аудиоданных.
- Освобождать обработанные буферы.
- Не хранить весь PCM часовой записи.
- Предусмотреть fallback при ошибке CUDA Out of Memory.
- Не допускать бесконтрольного накопления промежуточных файлов.

## NFR-03. Надёжность

- Не допускать потери уже сохранённых транскриптов после сбоя.
- Обеспечить повторную обработку незавершённого участка.
- Обеспечить безопасную отмену задания.
- Корректно обрабатывать отсутствие исходного файла.
- Отображать диагностируемые ошибки понятным текстом.

## NFR-04. Локальная работа

После установки, настройки PostgreSQL и загрузки модели программа должна работать без интернета.

Аудио, видео и транскрипты не должны автоматически передаваться внешним сервисам.

## NFR-05. Безопасность

- Хранить параметры подключения в пользовательской конфигурации.
- Не включать реальные пароли в репозиторий.
- Защищать пользовательские файлы от случайного удаления.
- Не запускать произвольные команды, составленные из непроверенных пользовательских строк.
- Учитывать возможность содержания персональных данных в транскриптах.
- Добавить явную функцию удаления истории и производных файлов.

# 10. Обработка ошибок

Необходимо предусмотреть:

| Ситуация | Требуемая реакция |
|---|---|
| Отсутствует FFmpeg | Инструкция по настройке |
| Недоступна PostgreSQL | Понятная ошибка подключения |
| Нет аудиодорожек | Отказ от задания с пояснением |
| Неподдерживаемый кодек | Ошибка с деталями ffprobe/FFmpeg |
| Файл удалён | Пометка задания и выбор нового пути |
| Недостаточно VRAM | Освобождение ресурсов и предложение более экономного режима |
| Недостаточно места | Остановка до записи новых временных данных |
| Сбой worker-процесса | Статус INTERRUPTED и возможность продолжения |
| Повреждённый участок | Повторная попытка; при неудаче — сообщение об ошибке участка |
| Ошибка экспорта | Сохранение транскрипта без изменения |

Все исключения должны логироваться с идентификатором задания.

# 11. Тестирование

## 11.1. Unit-тесты

Проверить:

- Расчёт таймкодов.
- Разбиение на участки.
- Перекрытия границ.
- Устранение дублей.
- Формирование TXT/SRT/JSON.
- Переходы состояний задания.
- Обработку текстовых сегментов.
- Поведение словаря терминов.

## 11.2. Интеграционные тесты

Проверить:

- Подключение к PostgreSQL.
- Миграции Alembic.
- Создание и выполнение заданий.
- Корректное сохранение сегментов.
- Восстановление после аварийной остановки.
- Обработку FFmpeg-файлов.
- Корректную работу с несколькими аудиодорожками.

## 11.3. End-to-end тесты

Тестовые записи:

1. Русская речь продолжительностью 5 минут.
2. Русская речь продолжительностью 60 минут.
3. OBS MKV с двумя независимыми дорожками.
4. Запись с большим количеством пауз.
5. Запись с технической терминологией.
6. Запись с шумами и перебиваниями.
7. Файл размером больше 1 ГБ.
8. Запись длительностью не менее 3 часов.

Необходимо проверять целостность текста, корректность таймкодов, завершение заданий и сохранение результатов.

## 11.4. Проверка качества распознавания

Подготовить тестовый набор русскоязычных записей с эталонными транскриптами.

Метрики:

- WER — Word Error Rate.
- CER — Character Error Rate.
- Доля пропущенных речевых участков.
- Количество необоснованных повторов.
- Ошибки технических терминов.
- Корректность временных меток.

Для первичного MVP целевой ориентир: WER не выше 15% на специально подготовленном наборе чистой русской речи.

Для шумных записей и технических терминов показатели должны оцениваться отдельно. Нельзя обещать одинаковое качество на всех источниках.

Метрики WER и CER вычисляются на исходном RAW-транскрипте после согласованной нормализации эталона и гипотезы, а не на вручную исправленной версии.

### 14.4. Диаризация

### 14.5. Live-режим
